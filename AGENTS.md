# AGENTS.md

Omaville draws the omacom GitHub org as a living city on the Omarchy logo, in the style of a monochrome isometric white-model of a cyberpunk arcology (see Visual style). Each repo is a building. Height is history (lifetime commits, one log scale for every building); light and motion are now (lamps, belts, drones, workers follow the last 7 days). It is one SvelteKit app (Svelte 5, adapter-node, plain JavaScript): the page and its chrome, and inside the same server the relay, which is the single source of truth: it scans the org, keeps the layout, the snapshot and the event log in Postgres (Drizzle), and serves them.

## Run and check

`just` lists the same commands as recipes (`just dev`, `just members`, `just check`, `just test`, …). Every environment variable the app reads is in `.env.example` (copy it to `.env`, never commit `.env`; an empty value means unset); add a new one there when you read it.

```sh
pnpm db:start                                     # Postgres in Docker (compose.yaml), at the DATABASE_URL in .env.example
pnpm dev                                          # the city on :8080, the relay inside (unsigned hooks): a scan of the org with GITHUB_TOKEN, else dev/snapshot.json; without DATABASE_URL an in-memory PGlite
pnpm dev:members                                  # the same with an invented members' city (wards, a private repo), signed in as "you" (always its own in-memory PGlite)
pnpm db:generate                                  # after a change to src/lib/server/db/schema.js: a new migration in drizzle/ (the app applies them as it starts)
pnpm db:studio                                    # browse the database
node scripts/check.mjs                            # draws the city at all 4 azimuths (the renderer's SVG build, the check's oracle) + both 3D recordings; fails on NaN/undefined
pnpm build && node build                          # the production app; deployed as the Dockerfile's container (Coolify), environment in .env.example
pnpm shots                                        # screenshots of the build, light and dark (needs Chrome)
pnpm fire -- --kinds push,merge,release           # fire signed sample webhooks at the dev app (CITY_WEBHOOK_SECRET signs them)
pnpm test                                         # the relay's tests, a build, then the end-to-end privacy test (scripts/test-privacy.mjs)
pnpm load -- --relay http://localhost:8080        # load test: 200 pages, one event a second (the dev app only)
node scripts/basecamp-hooks.mjs --url <app>/hook/basecamp/<key>   # register the Basecamp webhook on every project (dry run without --apply)
```

Run `check.mjs` after any change to `src/lib/city/city.js`, `kit3d.js` or `grid.js`. It fails on NaN, on a drawing that differs between two builds of the same data, and on a station kind with no `data-kind` row in the legend (`src/lib/ui/Legend.svelte`): a new kind of station needs a legend row saying its signal, formula and window. For visual changes, open the page in both themes. In dev the relay lives on `globalThis` across hot reloads: after changing server code, restart `pnpm dev`.

## Layout

- `src/lib/city/`: the renderer and what both sides share (`city.js`, `grid.js`, `kit3d.js`, `kit/`, `plugins/`, `stations.js`, `effects.js`, `trail.js`, `history.js`, `lod.js`). Pure; the scripts import it too.
- `src/lib/view/`: the 3D map: `map3d.js` (three.js, with `scene3d.js`, `fx3d.js`). There is no flat view: the renderer's SVG build (`buildCity` without `three`) is `check.mjs`'s oracle and the format the stations are sliced from.
- `src/lib/client/`: the browser's runtime: `runtime.js` (drawing in a worker, in-place patches, the live stream, snapshots, the water tower, the arrival), `model.js` (what the chrome reads from the model), `live.js`, `replay.js`, `film.js`, `clip.js`, `cinema.js`, `arrival.js`, `auth.js`, `worker.js`.
- `src/lib/ui/`: the chrome as Svelte components (`City.svelte` wires them; `city.svelte.js` is their state), on shadcn-svelte components in `src/lib/components/ui/`.
- `src/lib/server/`: the relay (`relay/`), the collector (`collector/`), the layout engine (`engine.mjs`), sign-in (`auth.js`, `gate.mjs`), the database (`db/`: the Drizzle schema and `connect()`, which applies `drizzle/`'s migrations), the dev sample (`sample.mjs`) and `city.js`, which makes the one database connection and relay per process from the environment.
- `city.config.json`: the one config file, the org (identity, rules, sources) and its layout setup (`layout`: landmarks, districts, mirrors, kits, the slots' words). Everything else is the org's data and lives in the database: repositories, people and their names (GitHub profiles), teams (the org's GitHub teams), activity, and the layout itself. Never put data about the org in a file (no name lists, aliases, team lists or generated layouts), and never write the org's name, repositories or words into the code.
- `dev/snapshot.json`: the one data file in the repository, a public snapshot for `pnpm dev` without a token, `check.mjs` and the tests (`pnpm collect` refreshes it).
- `src/routes/`: the page (`+page.svelte`, its load brings the city's data) and the relay's endpoints as `+server.js` routes; `src/hooks.server.js` starts the relay and resolves who is signed in.

## Pipeline

The relay owns the city's data; the code holds no data, and GitHub Actions only checks the code (`.github/workflows/city.yml`). Screenshots are local: `pnpm shots`.

1. `collector/scan.mjs` scans the org into a snapshot (data.json's shape); the relay runs it every hour (`CITY_SCAN_EVERY`, minutes), `scripts/collect.mjs` runs it once from the command line. `collector/public.mjs` is the public guard the relay applies to every snapshot it serves.
   - `github.mjs` uses the GitHub API with `GITHUB_TOKEN`. Forks and mirrors (GitHub's flags, or `config.layout.mirrors`) are read for their metadata alone, never their commits, branches or contributors: they stand at the base of the scale, unlit. The org's own repositories' commit counts and branches come in small batches (`DETAILS`), since GitHub times out a query past 10 seconds; a repository it cannot count keeps its last count (`scan.mjs`).
   - `git.mjs` reads local bare clones.
   - `basecamp.mjs` reads Basecamp when `config.basecamp.account` and `BASECAMP_TOKEN` are set: projects, people, to-do lists and hill charts, card tables, message subjects, check-ins and files, and the progress report (never bodies, comments or chat).
   - `aggregate.mjs` turns the sources into data schema 3 (plus `wards` with Basecamp).
2. `server/engine.mjs` places repos using the rules in `city.config.json`'s `layout` (pure; the relay runs it on every base, and its state object for a repository created live).
   - The layout lives in the database (the members' state's master layout in `meta`); a new database lays the city out from its first base, and after that it only grows. Never reorder or rewrite it. Existing positions must not move. Districts are slot arrays: index i is parcel i of that district in `src/lib/city/grid.js` (`PARCELS`), `null` is an empty slot, and an index never shifts. Besides those and the lots it holds `kinds` (a lot repo's district kind when its district was full), `houses` (one tower per contributor, 7 to 9 to a cell, in rings around the mark, nearest the arcology first; same-run arrivals in a seeded shuffle, never sorted by size) and `born` dates; a repo missing from the data keeps its lot as a vacant lot. A lot never lowers the skyline (`sceneryHeight()` in `grid.js`), and when the mark's lots are full, lots open in the same rings as the houses (`ringOrder()`); the layout never fails or skips a repo.
3. `server/relay/` is the live spine.
   - `events.mjs` maps GitHub webhook payloads to city events (one schema, fixed kinds, stable ids); `log.mjs` is the append-only log in the `events` table (an id is appended once; the public projection drops private repositories). Every database call is async; the relay runs appends, folds and base swaps one at a time (`serial`), in log order.
   - **The database** (`db/schema.js`, Drizzle on Postgres): `events` (the log: the event as `jsonb`, with its id, time, kind, repository, actor and a private flag), `meta` (the base: the latest public and members' snapshots and the master layout), `checkpoints` (the first base of each UTC day, for replay), and Better Auth's `user`, `session`, `account` and `verification`. `DATABASE_URL` is `postgres://…`; `pglite:memory` or `pglite:<folder>` runs PGlite in-process instead (dev without Docker, and the tests). Change the schema, then `pnpm db:generate`, and commit the migration (applied on connect under an advisory lock on Postgres, so overlapping containers migrate one at a time).
   - `relay.mjs` is the relay as one long-lived object on Web Requests and Responses: it scans on its own schedule, keeps the base snapshot and layout in the database and answers the routes: `data.json` and `layout.json` (the city now), `POST /hook` (signature checked), `GET /events` (Server-Sent Events: `city` per event, `snapshot` per new scan, catch-up by Last-Event-ID, `resync` when a catch-up was cut short), `/events/recent`, `/status` (counts only, never a repository's name), `POST /scan` and `POST /snapshot` (with `CITY_SNAPSHOT_TOKEN`). `/film`, `/state/at` and `/events/between` keep their answers while the log's top stands (`x-cache`). The page's config comes through `publicConfig()` (`collector/public.mjs`): the layout's words and slots, never a repository that was ever private, a mirror, a hint or a matching rule. `CITY_DATA` makes a file the base instead (local work). `server/city.js` reads the environment; the `Dockerfile` is the deployed container (Coolify).
   - `state.mjs` is the state object's fold: the latest snapshot and layout are the base (the relay's own scan, a `CITY_DATA` file, or `POST /snapshot`), every newer event is folded onto it, and each event goes out with a delta (the signals it changed per repository). Newer means past the base's log watermark (`seq`, the log's top when its scan began; a base without one goes by time). A base is prepared (the log read) and then committed in one step, so the two states and the database swap together. A `repo.new` places the repository with the layout engine; its delta carries the new layout and where it landed.
   - **Two cities.** One scan yields the public and the members' snapshots (`scan({ projection: "both" })`); the relay keeps a members' state (everything) and a public state over the same log. The members' state owns the master layout, which remembers every repository that was ever private (`layout.private`); the public layout is `publicLayout(master)`, the same positions with private repositories cut out, so nothing about them shows and positions agree. `/layout.json` always serves the public layout.
   - **Sign-in** (`server/auth.js`): Better Auth with GitHub (built in) and Basecamp (37signals Launchpad through the generic OAuth plugin), on its Drizzle adapter in the app's database, callbacks at `/api/auth/callback/<provider>`. Invite-only at every sign-in (`gate.mjs`): an org member (checked with the app's token), a verified email on `people.invited`, or an identity on `basecamp.account`. Off unless `BETTER_AUTH_SECRET` and a provider are set, and while it is off the relay runs the public city alone (`members: false` in `createRelay`): the scan and backfill skip private repositories and Basecamp, private webhook events are dropped before the log, Basecamp's hook answers 404. Without `CITY_WEBHOOK_SECRET` GitHub's hooks are refused and the scans alone update the city. `src/hooks.server.js` sets `locals.member`; `/members/data.json`, `/members/layout.json`, `/members/events` and the rest answer only with a session, and the page's load gives the members' city to someone signed in. Private repositories carry ◆ on their dock and "private" on their card. `pnpm dev:members` signs everyone in as "you" (only with `CITY_INSECURE` or in dev).
   - `welcome.mjs`: on a first-time contributor's merged public pull request, one comment with a link to their house (`/?house=<login>`); off unless `CITY_WELCOME=1` with `CITY_PUBLIC_URL` and `CITY_COMMENT_TOKEN`.
   - **Basecamp (members only).** `relay/basecamp.mjs` maps Basecamp's per-project webhooks (`POST /hook/basecamp/<CITY_BASECAMP_HOOK_KEY>`) and scan diffs (`project.new`, `hill.move`) to private ward events; the members' state folds them into `data.wards`. `scripts/test-privacy.mjs` proves none reaches the public stream or endpoints, and that the members' endpoints refuse without a session.
   - **History.** `POST /backfill` reads the org's whole history (commits, merges, releases, and Basecamp's progress report) into the log once; `GET /film` sweeps it into the year film's monthly frames (`relay/film.mjs`, `client/film.js`); `/events/between` and `/state/at` serve the replay. `GET /logos/<file>` proxies omarchy.org's patron images (that folder only) so WebGL may read them.
   - **In place, not reloads.** A delta (or a new snapshot whose layout, repositories, contributors and day window hold) redraws only the stations it changed: the builder worker runs `buildCity` with the new data and `city/stations.js` slices out those stations' `<g data-station>` groups, which the map swaps in the scene (`replaceStations`; a repository's windows and lamps are their own objects for this). A station's groups must carry their own position (`lift()` puts the deck transform on a single station group); `check.mjs` fails when a repository does not slice cleanly. A repository created live takes its cell in place too: whatever stood there (scenery, props, an empty parcel) is drawn inside `<g data-cell="i,j">` or `<g data-cell="apps:5">` (the `CELL` context in `city.js`), which the page removes before drawing the new station; a lot's plinth belongs to its station. A swapped station morphs in (a short rise). A new ring or a new landmark still reloads.
4. The page.
   - `+page.svelte` mounts `ui/City.svelte`, which starts the runtime (3D; a browser without WebGL is told so) and wires the chrome: `Header` (with `Search` and the totals), `Crew` (people), `Detail` (the overview and every kind of card), `Days`, `Tools`, `Tip`, `Legend`. The map's calls (`setLit`, `pick`, `focus`, `home`, `zoom`, `orbit`, `fx`, `trail`, `arrive`, `state`/`restore`, …) are the chrome's one API to it.
   - The live stream: `client/live.js` queues and rate-limits events, `city/effects.js` maps each kind to primitives that `view/fx3d.js` draws. Effects are finite and leave nothing behind.
   - Around them: `replay.js` (the scrubber), `arrival.js` (first visit and catch-up), `city/trail.js` (a person's or team's week), `clip.js` and `film.js` (videos, 3D), `cinema.js` (`?mode=cinema|kiosk|screensaver`; `omarchy/omaville` runs it on an Omarchy desktop), `city/lod.js` (level of detail in pixels per city unit).
   - The water tower (a scenery cell in the service yard behind the courtyard, never a lot) shows the relay's health: the runtime sets `data.health` from `/status` and the stream, and redraws only that station.
   - `.github/workflows/city.yml` checks the code on every push and pull request; Coolify builds the `Dockerfile` and deploys on a push to master.

## The renderer (read before touching it)

- **`src/lib/city/city.js`** is the only place buildings are defined.
  - It is pure: data, layout and azimuth go in, an SVG string comes out.
  - Painter's order comes from `ordered()`. Face-dependent details use `VX`/`VY` and `nearX`/`nearY`, so the city draws correctly from all four azimuths (72/162/252/342).
- **3D is not a separate model.** `buildCity({ three: true })` swaps in `kit3d.js`, which records 3D primitives instead of projecting them.
  - `view/scene3d.js` parses that record into three.js.
  - It records twice, at az 72 and 252, and merges the window panes and signs so all faces have them.
  - Any new primitive must work through both kits (`kit/iso-kit.mjs` for SVG, `kit3d.js` for 3D).
- **Coordinates:** city units, z up. `PZ` (12, `grid.js`) is the deck: buildings that carry the height scale stand at it, on a stroke or on a plinth (lots, quarter blocks), so the scale starts from one level. The 3D world group is mirrored in y (`scale.y = -1`) so it matches the SVG. Text textures are flipped for this; see `textPlane`.
- **One repository, one parcel:** every repo has exactly one building, drawn by `parcel()` with its district's kit (`KITS`), and everything else about it (pallet of open PRs, branch capsules, workers, name) stands on its own dock via `dock()`. Never draw a repo's data anywhere else; a new district needs a parcel list in `grid.js` and a kit.
- **Landmark slots:** the mark's hand-built stations are slots, not repositories: `hall`, `press`, `disc`, `dispatch`, `works-1`…`works-4`, `pod-1`, `pod-2` (`LANDMARK_AT` in `grid.js`, `SLOT` in `city.js`). A repository takes one with `config.city.landmarks`; the slot's kind of station (`config.city.kinds`), its card's text and its signs (`config.city.signs`) come from the config, with generic defaults. The billboard towers are `BOARDS` cells; their text is `config.city.boards`.
- **Screens:** a billboard is a lit screen: an `ow-holo` path with `data-glow` (its hue), in a bezel. In 3D it is an emissive shader (`scene3d.js`: scanlines, a band that sweeps up, a rare flicker, the map's clock in `mats.screenUniforms`) that blooms in the dark theme; the words and marks on it carry `data-screen` and are drawn white, after the screen (`renderOrder`). A `data-ticker` sign is a crawl of the latest commits (`map3d.js` redraws it).
- **Stations:** wrap a building in `<g data-station="repo">` to make it pickable and lightable. `data-worker`, `data-pallet` and `data-rack` (the capsules) mark secondary parts that don't steer the camera.
- **Randomness:** must be seeded per lot (`seed = …` and `hash()`), so adding a repo never reshuffles its neighbours.
- **Plugins:** `src/lib/city/plugins/` holds building kits and effects added by pull request (see `plugins/index.js` for both shapes). A kit draws one kind of building at the height the one scale gives it; a repository takes one with `config.kits`. An effect adds a new event kind with its webhook mapping. `check.mjs` checks each plugin's schema, legend row, footprint and determinism.
- **Wards:** a Basecamp project's ward stands on a civic cell (`layout.wards`, placed once near the repositories it steers, from a repository's hint file (`config.hints`) `project:` line). Its form has no height scale; only its parts carry data. The public city draws it dark and unlabelled.
- **Vendored code:** `src/lib/city/kit/` is the anatomy kit (MIT; don't edit it). three.js r169 comes from npm (`three@0.169.0`).

## Visual style

**A monochrome isometric white-model of a cyberpunk arcology, drawn like a technical plate.** Every change should strengthen one of these three layers and break none of them:

1. **Technical plate (the drawing).** Axonometric line art: thin, even outlines, flat tone shading, an orthographic camera (no perspective), no gradients or textures, small mono labels ("Fig 1", stencil text on the ground). Think patent drawing or engineering plate. In 3D: orthographic camera, crisp edge lines, non-photorealistic shading.
2. **White model (the material).** Like an architect's card or foam-board massing model: everything is one material in a few grey tones, and form comes from light and shade alone. Windows are flat panes in slightly darker grey, never colour.
3. **Cyberpunk megastructure (the architecture).** The cyberpunk lives in the forms, not in neon:
   - setback towers;
   - an arcology spire with a sky deck;
   - Kowloon-style megablocks with bolted-on capsules;
   - Metabolist stacked "jenga" towers;
   - cooling towers, sky bridges, antennas, blade signs and holo billboards.

   Density and verticality are welcome; empty ground is not.
   The contributors' quarter reads as a city: blocks on kerbed plinths cut by avenues (every third cell) and a ring road, with civic cells (stadium, monument, park, plaza, transit station) fixed per cell by `civicAt()` in `grid.js`.

**Rules that follow from the style:**

- **Colour means life, or a sign.** `--ow-accent` (cyan) is for selection, hover and focus, `--ow-live` (magenta) for pulse lamps, tail lights and alerts. Four quiet signage hues (`--ow-glow-c|m|a|v`: cool blue, magenta, amber, violet; `PALETTE.glow` in 3D) belong only to signs, patron screens, monuments and street light, set with `data-glow` on a neon line, sign, holo panel or dot group. Keep them subtle and never let one mean a count. Add no others.
- **References** when in doubt: patent drawings and Moebius for line; Superstudio and Archigram's Plug-in City for the model; Syd Mead, *Ghost in the Shell* and Nihei's *Blame!* for the city.
- **Light is now.** A window pane carries `data-on` when its station had a commit in the last 7 days (`ON` and `withOn()` in `city.js`: wrap a station's building in it); a quiet building's panes go dark. In the dark theme the lit panes, the neon, the lamps, the signs and the effects bloom: in 3D anything that should glow sets `userData.bloom` (everything else is drawn black in the bloom pass, `map3d.js`), and the plate's neon `.ow-bloom` paths show. The edge lines fade toward the far view (`edgeAlpha()` in `city/lod.js`, both views), so from the home zoom the city reads by its faces and its lights.
- **Data first.** Height, lamps, belts, drones and billboards encode real activity. Anything decorative is scenery and the legend says so. Never invent data. Laws: nothing is drawn without a legend row (signal, formula, window); height is history and light is now; position is permanent; same data, same city, byte for byte (randomness seeded per lot, never `Math.random`); scenery stays below 60 and never sits on a data lot.
- **UI chrome** is shadcn-svelte in the Lyra style (boxy, JetBrains Mono, Phosphor icons at light weight; Tailwind 4), on the city's palette: `src/routes/layout.css` maps its tokens onto the plate's glass, hairlines and inks (`--ow-*`, `--anatomy-*`). Light and dark come from mode-watcher (`<ModeWatcher />` in `+layout.svelte`): the system's mode, or the viewer's from the toolbar's toggle or `?theme=`, as the `.dark` class on `<html>` (Tailwind's `dark:` variant and the page background) and as `data-theme` on the app's root (the plate's own CSS and the 3D palette). Every part of the chrome uses shadcn-svelte's component where it has one (Card, Button, Tooltip, ToggleGroup, Badge, Command for the search, Sonner for the status, Progress for the bars, Chart for the day bars, Slider for the scrubber, Sheet for the legend, Avatar, ScrollArea); the map's hover card is the one exception (a Card placed by hand: no component follows a pointer over a canvas). Add components with `pnpm dlx shadcn-svelte@latest add <name>`; use them through `ui/Panel.svelte` (a card), `ui/IconButton.svelte` (an icon button with its tooltip) and `ui/Icon.svelte`. `src/app.css` holds the chrome's layout and the plate's own styles; it is unlayered, so it wins over Tailwind's utilities: don't restyle a shadcn component there. Glass cards with hairline rings, mono eyebrow labels, "−" to collapse a card into an icon button. `fitChrome()` (in `City.svelte`) keeps the header, cards and dock from overlapping at every width; keep it that way.
- **Both themes.** Every change must hold up in light and dark. The dark theme is the monochrome white model above. The light theme is the same model in colour, a realistic palette: plaster and concrete faces, sand ground and asphalt roads, blue glass (dark when quiet, sky or warm when lit), green parks, water, saturated signage; `PALETTE.light` in `view/scene3d.js` and the `.iso.ow-root[data-theme="light"]` tokens in `src/app.css`, and nowhere else. Materials go by use (`MATERIAL` and `withMaterial()` in `city.js`: brick workshops, render on the works and pods, concrete decks, plinths, scenery, coolers, plazas and stadiums, steel masts, machines, belts, boards, tanks and barrels, zinc silos and sheds, timber crates, safety-yellow forklifts, lawns and leaves in the parks, four stuccos for the houses fixed by login, plaster elsewhere; the boulevard's roadway is asphalt (`ow-road`)); a solid may name its own (`className: "ow-mat ow-leaf"`). The plate colours a material in CSS (`.ow-<name>{--m}`, its shades mixed from it) and the 3D record carries it as `data-material` to a named material in the palette; where a palette does not name it (dark), the face tone stands.
- **Patrons: corporate only.** The city draws the founding corporate patrons on the arcology's crown and the distinguished corporate patrons on billboard screens (then gantries across the ring road), each with its logo as a single-tone stencil. No individual patrons: no founders' wall, blade signs, patrons' walk or house marks.

## Data notes

- People (`config.people.who: "all"`) are everyone who committed in the window, plus org members (named by their GitHub profiles, with their GitHub teams in the members' city), plus (members only) everyone with Basecamp work, merged by login, then email, then name. Org members carry `member: true`; bots are excluded by `config.bots`; `config.people.hidden` (names, logins or emails) are counted but never drawn; `config.people.invited` (emails) may sign in without org membership. The browser gets only `org`, `window`, `primary`, `names`, `city`, `kits` and `patrons` from the config (`+layout.server.js`).
- `wards` (members): per project, its name, link, linked repositories, hill (`[title, position]`), card columns, to-dos open and done, lists under way, messages and events this week. The public snapshot keeps only `{ repos }` per ward; `collector/public.mjs` refuses anything more, any Basecamp-only person, work count or avatar.
- Data schema 3: `total` is lifetime commits on the default branch (a fork counts only what is ahead of upstream, a mirror 0) and is what height follows; `c30`, `c7`, `people7` are the recent-activity signals; `at7` and `botAt7` place each commit of the belts' week (the last 7 calendar days) at its time, 0 to 1. The window is whole UTC calendar days ending today. `contributors[]` (lifetime commits per login over public repositories) feed the houses; `patrons[]` (the tiers of omarchy.org/patrons, from omarchy-site) feed the crown and billboard signs.
- Two projections: the collector writes the public city by default (no private repos, people by login, no teams, membership only when public); `--projection members` keeps everything. `scripts/assert-public.mjs` guards a public file. Never put private data in `dev/snapshot.json`. The dev members' sample (`server/sample.mjs`) is invented, with made-up names, and lives only in the dev relay's memory.
- The first real run against the org used a member's `gh auth token` (read:org, repo). The org admin still has to install the GitHub App and add the city's Basecamp account to every project.
- Commits are de-duplicated by SHA, then by author email, author date and subject, then (git source only) by a change id from the files' blobs before and after (`pid`, see `collector/git.mjs`; the GitHub API source can't afford it). Merges and mirror repos don't count. Bot and routine commits (`config.bots`, `config.routine`, which cover Omabot and Claude) stay out of height, people, `c30` and `c7`; they ride the belts as their own per-day count, `repos[].bots`.
- `unmerged` counts distinct recent commits that exist only on branches.
- `generatedAt` changes only when the aggregate's `digest` changed (the collector reads the previous `data.json` via `--prev`), so pages don't reload for an empty run.
- The GitHub API collector has never run against the live org. Expect to fix small things the first time it runs with a real token.

## What's next

Read the plan doc: "Omacom City — the living city plan". Phases 0 to 5 are built. What remains is deployment and access, which the org's owners do: the GitHub App, the domain and the Coolify app with its Postgres, the Basecamp account on every project with its webhooks, the OAuth apps for sign-in (GitHub and Basecamp Launchpad, with the callbacks above), and a run of `POST /backfill`. The Basecamp side and sign-in have only run against mocks and local redirects so far: expect small fixes on the first real run.

Don't commit tokens. `dev/snapshot.json` is a real public snapshot of the org for offline work.
